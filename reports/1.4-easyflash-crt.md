## Bank layout (v0.1)

EasyFlash: 64 banks, each with an 8K ROML chip ($8000) and an 8K ROMH chip ($A000, or $E000 in Ultimax mode).

| Bank | ROML ($8000) | ROMH ($A000/$E000) |
|---|---|---|
| 0 | Launcher (CBM80, 190 bytes) + TSB Neo image $8000–$9F40 | **Boot code** with the reset vector (`additions/easyflash/ef_boot.a`) |
| 1 | TSB Neo image, continued | free |
| 2 | TSB Neo image, end ($50BE bytes into the stream), rest $FF | free |
| 3–63 | free (reserved: Ultra code, overlays, tables) | free |

ROML banks 0–2 are the released Magic Desk CRT's banks 0–2, byte for byte, except **two bytes**. Magic Desk switches
the cartridge off with `lda #$80 : sta $de00`; EasyFlash needs `lda #$04 : sta $de02`. The bank register is $DE00 on
both. [Certain: `tests/ef_tsbultra.py` diffs the chips.] The TSB image comes from the source:
`build/tsbneo_ref.bin` = the disk build with the key-table padding at $C657–$C74F written as $00 instead of the source's
$EA. With that, it equals the released image exactly. [Certain]

The released CRT's banks 3–4 (TSB.MEM, TSB.HSG, TSB.MON, TSB.EXT) are **not** copied. The TSB image in the released CRT
is the *disk* build (`cartridge = 0`): it loads those overlays from disk and never touches the cartridge again. [Certain:
the image matches the disk build, and the disk build has no $DE00 access.] The `cartridge = 1` source variant, which
would load overlays from Magic Desk banks, was never released. It differs in other ways too: keyword 64 is MONITOR
instead of SECURE, and LOCAL/GLOBAL give BAD MODE.

## Boot sequence

1. Power-on or reset: the EasyFlash starts in Ultimax mode with bank 0, and the CPU takes the reset vector from
   ROMH bank 0.
2. `ef_boot.a` (at $E000):
   - copies a 6-byte trampoline to $0200;
   - reads the keyboard column with the Commodore key;
   - jumps to the trampoline.
3. The trampoline writes $DE02: `$06` (8K mode, ROML at $8000) normally, or `$04` (cartridge off) with the Commodore
   key down. It then jumps to the KERNAL reset at $FCE2.
4. 8K mode: the KERNAL finds CBM80 in ROML bank 0 and runs the launcher:
   - the same KERNAL init calls, colours and lower-case mode as the released CRT;
   - it copies $8000–$CFFF from banks 0–2 to RAM, switches the cartridge off and jumps to TSB's cold start.

   Cartridge off: the KERNAL boots a stock C64.

TSB Neo's own marker at $8004 is "cbm80" in lower-case PETSCII ($43 $42 $4D). The KERNAL does not accept it, so TSB
in RAM never autostarts and GO 64 needs no clean-up. [Certain]

## GO 64 path

- In v0.1 the GO 64 path is triggered by the Commodore key held at reset.
- In the finished cartridge, Ultra's `GO 64` command (task 5.1) will enter the same path.
- Neo stays byte-identical and has no GO 64; from Neo, the user resets.
- The test cannot press a matrix key through VICE's binary monitor. Instead it stops at the key test (`keytest` in
  `build/ef_romh0.lbl`) and sets the A register to "key down".

**Decision for you (D-1.4a):** keep "Commodore key at reset = stock C64" in the finished cartridge? I recommend
**yes**. It is the usual EasyFlash escape hatch, it costs nothing, and it is the only way from Neo to a stock C64
without power-cycling with the cartridge removed.

## SHOW DRIVES is timing-fragile (also on the released CRT)

The first EasyFlash run of SHOW DRIVES ended with `?DEVICE NOT PRESENT ERROR IN 230`. The cause:
- The program checks `ST=-128` exactly.
- Device 16 sometimes answers −125 (not present, plus timeout bits). That depends on when RETURN is pressed relative to
  the emulated drive.

I pressed RETURN 0–5 frames later than the scenario does:
- the released CRT fails at +3;
- the EasyFlash CRT fails at +0;
- every other delay passes on both. [Certain]

So the failure is in the demo, not in the EasyFlash code. The scenario now presses RETURN one frame later, which passes on
both; the golden is unchanged. This will come back with Ultra's different timing (G4). A real C64 can probably hit it too
[Likely].

## Hardware risks found (for tasks 2.1 and 6.2)

1. **EasyFlash RAM at $DF00–$DFFF overlaps the REU registers.** With EasyFlash plus a 512K REU in VICE:
   - `PEEK($DF00)` returns EasyFlash RAM (255) instead of the REU status (16);
   - REU DMA still works, because it is started by writes; the REU scenarios pass.

   Programs that read REU registers (detection, status) get EasyFlash RAM. On real hardware, an EasyFlash plus a separate
   REU drive the bus together on reads [Likely]. How an Ultimate 64 / 1541 Ultimate behaves with EasyFlash emulation and
   its REU both on is unknown [Guessing]. IMG VIEWER always runs with an REU (decision 5), so **test this on real
   hardware in task 2.5**.
2. **TSB Neo writes $DF01–$DF08 at boot** (the REU check of MEMHOOK). Without an REU these writes land in EasyFlash RAM.
   **Ultra's bank-switching core in EasyFlash RAM (task 2.1) must avoid $DF00–$DF0A.** Neo's MEM/NRM/INST with an REU
   write there again. [Certain from source; observed in VICE: $DF01/$DF02 read 0 after boot.]
