## Findings

### 1. TSB Neo MERGE without a device number fails under the JiffyDOS KERNAL [Certain, VICE]

`MERGE "PART"` replaces the program in memory instead of appending to it; in the `tsb_session` scenario the session
then crashes (PC in zero page). `MERGE "PART",8` works.

- MERGE calls BASIC's "get LOAD/SAVE parameters" at $E1D4 (in the KERNAL chip), then LOAD with A=0 and X/Y = end of
  program.
- Stock: $E1DD is `JSR SETLFS` with X=1, Y=0: device 1, secondary address 0. TSB's LOAD hook turns device 1 into its
  drive; SA 0 makes LOAD relocate to X/Y, so the file is appended at the end of the program.
- JiffyDOS: $E1DD is `JSR $F73A` (default-drive routine): device 8, but LA and SA are $6F. With SA ≠ 0 the LOAD is
  absolute: the file goes to its header address $0801 over the program. LOAD returns end $081A instead of $0830 for
  the same 25-byte file.
- With `,8` BASIC's parser calls SETLFS again with Y=0, so SA is 0 and MERGE works.
- On real hardware the same ROM does the same [Likely].
- `tsb_session` is marked KNOWN for kernal=jiffy. Neo stays byte-identical, so the bug stays in Neo.

**Decided (D-2.0a):** Ultra fixes it; Neo keeps it. Test: `merge_nodev` (see Decisions below).

### 2. SHOW DRIVES under the JiffyDOS KERNAL [Certain, VICE]

Fails on pal-jiffy-stock and ntsc-jiffy-stock with `?DEVICE NOT PRESENT ERROR IN 230`. The demo skips a device only
when `ST=-128` exactly; an absent device sometimes answers −125 (not present plus timeout bits), depending on bus
timing. The same fragility is in reports/1.4-easyflash-crt.md (stock KERNAL, other keypress timing). In a plain loop
`OPEN1,I,15:CLOSE1:PRINT ST` for devices 8–30 under Neo, the JiffyDOS KERNAL gives −125 for device 16 and −128 for the
others; the stock KERNAL gives −128 for all. Since the deterministic typing (finding 6) it also fails on pal-jiffy-jiffy
(RETURN delay sweep in the Result section), so it is marked KNOWN for kernal=jiffy with either drive ROM. Not TSB behaviour; a real C64
with JiffyDOS and a stock drive can probably hit it too [Likely].

### 3. JiffyDOS function keys

Neo switches them off at boot (`stx $9b`, TSBneo/tsbneo.a line 336). After boot on the JiffyDOS KERNAL, $9B = $80 with
both CRTs (no cartridge: $00) [Certain]. That this disables the keys is from the source comment [Likely]: the harness's
held-key method writes the key code after the KERNAL scan, so it cannot trigger JiffyDOS's F-key handling, and no
keypress test was made. Ultra must do the same (CLAUDE.md).

### 4. Music demos on NTSC: harness window, not TSB behaviour [Certain, VICE]

MUSIC1-WTEXT, MUSIC2-3VOIC and MUSIC3TRIPLT failed on NTSC ("sid trace differs") with both CRTs.

- The trace is sampled at every KERNAL IRQ (entry $FF48), not per video frame. That IRQ is CIA timer A, which the
  KERNAL sets to ~60 Hz on both standards (latch $4025 PAL, $4295 NTSC). 1500 samples are ~25 s on both.
- TSB's music is clocked by that same IRQ (`sirq` → `sirqplay`, tempo counter per IRQ). Recorded per IRQ and lined
  up at the first note (first gate bit set), PAL and NTSC are:
  - MUSIC3: identical for all 2294 IRQs compared;
  - MUSIC2: identical for 1320 of 1321 IRQs; only the first IRQ differs (on NTSC voices 2 and 3 are already gated
    when the first sample is taken);
  - MUSIC1: identical except 27 IRQs at +1484: the program's own `WAVE1,$10` (line 570, gate off at the end) comes
    27 IRQs earlier on NTSC. The text is paced by `PROC WARTE` = `FOR W=1 TO 1815:NEXT`, a busy loop, and an NTSC
    C64 gets ~3% more CPU cycles per jiffy (more cycles per IRQ, fewer stolen by the VIC per IRQ).
- What moved the trace: the window started at RUN. The BASIC set-up before PLAY is CPU-bound, so the first note comes
  at IRQ 979 on PAL and 951 on NTSC (MUSIC2), and the window's end cut the song at a different place (NTSC traces had
  1–2 extra states at the end; MUSIC3 had one extra all-zero state at the start).
- So the music engine runs at the same tempo per jiffy on PAL and NTSC. The only real difference is MUSIC1's busy-wait
  text, which runs ~3% faster on NTSC, as it would on a stock C64; this is not TSB behaviour.
- Fix: the `sid` step takes `"from": "gate"` and starts at the first note. Windows: MUSIC1 1400 IRQs (before its
  CPU-timed gate-off: +1484 on NTSC, +1511 on PAL), MUSIC2 1500, MUSIC3 1200. Goldens recaptured on pal-stock-stock
  (released CRT). The three pass on all 8 machines on both CRTs (48/48).
- This also helps Ultra: its slower BASIC would have moved the old window the same way (G4).

### 5. DIRSELECT on EasyFlash + JiffyDOS drive: random box covers the expected text [Certain, VICE]

On pal-stock-jiffy with the EasyFlash CRT, DIRSELECT failed on `missing /ende mit/`, reproducibly. The selector box
is placed with `RND(0)` (seeded from the CIA timers), which is why the scenario already compares only text. With
this CRT/drive-ROM timing the box lands at the top and covers the "Ende mit '.'" line. The scenario now expects only
the disk name (`tsb neo 2.60228`); it passes there and on pal-stock-stock with both CRTs.

### 6. Load-dependent failures: random power-on RAM, fixed [Certain]

In the first gate runs, `check_detect_background` (EasyFlash, pal-jiffy-stock and ntsc-jiffy-stock) and
`check_detect_sprites` (EasyFlash, pal-jiffy-jiffy) failed with "sprites differs" and passed when rerun alone. The
earlier `tsb_sprites` failure (reports/1.4-easyflash-crt.md) was the same pattern.

**Cause [Certain]:** VICE's power-on RAM, not the typing. With the default `RAMInitRandomChance=10` VICE flips random
bits of the RAM pattern at power-on, from a seed that depends on the host clock. Runs that start in the same second
get the same flips. A run of check_detect_background 48 times (16 at once, a busy loop on each of the 18 host cores)
failed 16 times, all 16 started together, all on the same byte: sprites.bin byte 24 = the sprite 7 pointer at
$07FF, 4 instead of the golden's 0. CLS clears $0400–$07E7 only, so $07F8–$07FF keep their power-on value. With
`-raminitrandomchance 0 -seed 1` (VICE's plain pattern, fixed seed) the same 48-run test passed 48/48. My earlier
statement here that random RAM was ruled out was wrong: those 4 identical captures had started together.

**Typing:** the harness no longer uses VICE's keyboard-buffer feed (monitor command $72). `Vice.type()` queues the keys,
and at each KERNAL IRQ entry ($FF48) the harness writes them into $0277 and sets $C6 itself, whenever the buffer is
empty (up to XMAX, $0289, at most 10 keys). The emulation is stopped while it writes, so a key arrives at a fixed IRQ
count by construction [Certain]. Whether VICE's own feed actually depended on host load was not shown: with the
old method, 30/30 runs passed under the same load [Certain], and the typing fault of task 1.5 may have had another
cause [Guessing].

**Proof** (`tests/stress_typing.sh [crt] [machine]`): check_detect_background, check_detect_sprites and tsb_sprites,
10 times each, `-j 6`, a busy loop on every host core (18):

| CRT | Machine | Result |
|---|---|---|
| released (`build/TSBneo.crt`) | pal-stock-stock | 30/30 PASS |
| EasyFlash v0.1 (`build/TSBUltra.crt`) | pal-jiffy-stock | 30/30 PASS |
| EasyFlash v0.1 | pal-jiffy-jiffy | 30/30 PASS |

No golden was re-recorded. With both changes, `make test` and the full demo and command suites pass on pal-stock-stock
and ntsc-stock-stock against the existing goldens.

## $02A6 check

- TSB Neo's own code never reads $02A6 (PAL/NTSC flag) [Certain: tsbneo.a, memhook.inc and the overlays searched].
  Only the C128 extension `additions/vdcbasictsb.a` reads it (line 527: VDC timing for NTSC); it does not run on a
  C64.
- At READY, under both CRTs, both standards and both KERNALs, $02A6 holds what the KERNAL found: 1 on PAL, 0 on NTSC.
  CIA1 timer A counts down from $40xx on PAL and $42xx on NTSC, i.e. the KERNAL's $4025/$4295 latches, so the KERNAL
  IRQ (TI, keyboard, TSB's IRQ work) runs at ~60 Hz on both [Certain]. TSB calls $FDA3 (CIA init) at cold start; the
  monitor TSB.MON calls $FDDD, the KERNAL routine that picks the latch from $02A6 [Certain from source].
- So nothing in Neo depends on PAL vs NTSC except raster timing (next section). The full suites show where that
  matters at run time (see Result).

## tsbhsg.a check (TSB.HSG, High-Speed-Grafik, loaded by GRAPHICS at $7400)

- PAL/NTSC: the only timing code is the split screen (`£IS,from,to` / `£I1`). Its raster IRQ (`hsgirq`) waits for
  the next raster line, then a fixed delay loop (`ldx #27 : dex : bne`, ~135 cycles), then switches $D011/$D018/$DD00.
  Raster lines are row×8+$2F for rows 0–25 (≤ 247), valid on NTSC (262 lines) as well. No $02A6, no CIA timing.
  It exits through $EA81 (KERNAL IRQ exit; identical in JiffyDOS).
- Run in VICE (`10 £H:£IS,10,20:£I1`, GOTO loop, screenshots):
  - PAL: graphics on lines 80–159 of the display window, clean edges on all 320 pixels.
  - NTSC: the same lines, but each switch happens ~12 pixels early: the last 12 pixels of line 79 are already graphics,
    and line 159 ends 12 pixels early. The delay loop is tuned for PAL's 63 cycles per line; NTSC has 65.
    Cosmetic only. [Certain for one frame in VICE; whether it jitters between frames was not checked.]
- KERNAL/BASIC: TSB.HSG calls only $EA81 in the KERNAL chip, plus BASIC ROM routines ($AEFD, $B79E, $AF08, …), which
  JiffyDOS does not change.
- Coverage: TSBDEMO.DMO's PROC SPEED loads HSG with GRAPHICS and draws with `£K` (circles), `£B` and `£R`; the
  scenario `tsbdemo_exit_speed` (checkpoints speed1–4) runs it, so HSG's drawing is in the matrix. The split screen
  is used by no demo and no test; a scenario for it would need a picture capture (the harness compares memory, so the
  NTSC step above would not show up in a golden).

## TSB's KERNAL-chip calls outside the jump table

All `JSR`/`JMP` targets in $E000–$FF80 (the KERNAL chip, which also holds BASIC's tail $E000–$E4D2), excluding the
$FF81–$FFF3 jump table. Sources: TSBneo/tsbneo.a (+ memhook.inc) and additions/*.a; symbolic names resolved. Data
reads from the chip: only `lda $e3ab,x` (CHRGET copy, line 896) and `lda $ff00` (C128 MMU test, line 4104), both
unchanged in JiffyDOS. "JiffyDOS" = does the code executed from that entry differ in JiffyDOS 6.01 (checked by
disassembling both ROMs where a changed byte lies within 32 bytes of the entry).
