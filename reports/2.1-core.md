# Task 2.1 — Bank-switching core

Date: 2026-11-11. Plan task 2.1: "Bank-switching core: routines in EasyFlash RAM at $DF00–$DFFF clear of the REU
registers, fetch/store helpers, IRQ and NMI handling." Extra conditions (Fafa, 11 Nov): keep $DF00–$DF0A clear,
fast path for $0000–$7FFF and $C000–$CFFF, every spike test on pal-stock-stock and ntsc-stock-stock, JiffyDOS
machines at the gate. Labels: [Certain] = run or read here; [Likely] = strong inference; [Guessing] = plausible,
unchecked. All runs are VICE 3.10 x64sc; nothing here has run on real hardware yet (task 2.5).

## Result

**The core works in VICE: program memory under the cartridge, RAM under I/O and under the KERNAL, far calls
between banks, and interrupts in every memory configuration it uses. The spike test passes on pal-stock-stock
and ntsc-stock-stock, with about 87,000 IRQs and 75,000 NMIs landing inside the helpers and no error.** [Certain, VICE]

- Code: `additions/ultra/core.a` (core module and caller macros), `additions/ultra/spike21.a` (spike CRT and
  tests). `make build` makes `build/spike21.crt`; `make test` runs `tests/core21.py` on PAL and NTSC.
- Also run before this report: a clean `tests/matrix.sh gate` on both CRTs (reports/2.0-machine-matrix.md), which
  includes the spike on all 8 machines: all PASS.
- Size: 243 bytes in EasyFlash RAM ($DF0B–$DFFD, 2 bytes spare), 110 bytes plus the CPU vectors in the RAM under the
  KERNAL ($FF40–$FFAD, $FFFA–$FFFF; 76 bytes spare). $DF00–$DF0A is never written (checked by the test).
- Cost per access, measured and equal to the hand count (table below): FETCH 15–16 cycles on the fast path
  (`lda (zp),y` is 5), STORE 30–31 (`sta (zp),y` is 6); the slow path for $8000–$BFFF is 53 / 80. A far call
  costs 204 cycles round trip (`jsr`/`rts` is 12).

## Memory model

The interpreter and TSB run from flash in EasyFlash 16K mode ($DE02 = $07) with the CPU port at $37: ROML at
$8000–$9FFF, ROMH at $A000–$BFFF, I/O, KERNAL. The BASIC workspace is $0801–$CFFF (decided design), so
$8000–$BFFF of it lies under the cartridge. The core switches only the CPU port, never $DE02:

| Name | $01 | $8000–$BFFF | $D000–$DFFF | $E000–$FFFF | Used for |
|---|---|---|---|---|---|
| MODE_HOME | $37 | flash (ROML/ROMH) | I/O | KERNAL | all flash code |
| MODE_RAM | $35 | RAM | I/O (EasyFlash RAM at $DF00 visible) | RAM | slow path, under-KERNAL RAM |
| MODE_ALL | $34 | RAM | RAM | RAM | RAM under the I/O chips |

[Certain, VICE] for all three rows: T1 and T2 write every byte of $0800–$CFFF, $D000–$DFFF and $E000–$FF3F
through the helpers and read it back, read the RAM under the cartridge a second, independent way (through
MODE_ALL), and check that flash, I/O and the KERNAL are visible again afterwards. Writes in MODE_HOME also reach
the RAM under the KERNAL; the core uses that to install its $FFxx part. Real hardware: task 2.5.

Where the core lives:
- **$DF0B–$DFFD** (EasyFlash RAM): visible whenever I/O is (MODE_HOME and MODE_RAM). Holds the bank shadow
  `core_bank` ($DE00 is write-only), the two interrupt hook vectors, the slow FETCH/STORE, the IRQ/NMI wrappers, the
  far-call entry and the MODE_HOME halves of everything else.
- **$FF40–$FFFF** (RAM under the KERNAL): visible in MODE_RAM and MODE_ALL. Holds the CPU's NMI and IRQ vectors in
  RAM ($FFFA/$FFFE), the entry stubs for interrupts taken in those modes, the MODE_ALL half of the under-I/O
  helpers, and the stack shuffle of the far-call return. Free for the core because the U2+ bitmap at $E000 ends at
  $FF3F and the demo files loaded at $E000 end at $E7FF (THIN/RETROFAN/PUZZLE/KIRBY.SET) [Certain, from the D64
  directory]. A program that writes $FF40–$FFFF breaks interrupt handling in MODE_RAM/MODE_ALL; Ultra's POKE
  (task 3.4) has to keep it out [Likely needed; not checked against every POKE in the corpus].
- $DF00–$DF0A stays free: TSB Neo's REU probe writes $DF01–$DF08 (task 1.4) and an REU would have its registers
  there.

## Interface

For flash code, as ACME macros in `core.a` (each replaces one instruction or a call):

| Macro / routine | Replaces | Keeps | Cycles (measured) |
|---|---|---|---|
| `+FETCH zp` | `lda (zp),y` | X, Y, C, V; N, Z from the byte | 15 ($00xx–$7Exx), 16 ($C0xx–$FFxx), 53 ($80xx–$BFxx), 56 ($7Fxx) |
| `+STORE zp` | `sta (zp),y` | A, X, Y, all flags | 30 / 31 fast, 80 slow |
| `+IOFETCH zp` | `lda (zp),y` under I/O | as FETCH | 56 |
| `+IOSTORE zp` | `sta (zp),y` under I/O | as STORE | 83 |
| `+FAR target, bank` (stub, called with `jsr`) | `jsr target` | A, X, Y, all flags both ways | 204 round trip |
| `core_ld` / `core_st` | slow path only, any address in $0000–$FFFF except I/O | as FETCH / STORE | 28 / 41 + caller setup |
| `core_irqvec` | hook JSR'd in every IRQ | — | — |
| `core_nmivec` | NMI continuation (default KERNAL $FE47) | — | — |

Cycle counts: CIA 1 timer B with interrupts off and the screen blanked (badlines would add up to 40 cycles), the
empty measurement subtracted. Identical on PAL and NTSC, and identical to counting the instructions by hand
(e.g. far call: stub 43 + entry 51 + target `rts` 6 + return 98 + the caller's `jsr` 6 = 204) [Certain].

**Fast path.** FETCH and STORE test only the pointer's high byte, inline in flash: $00–$7E and $C0–$FF access
directly, $80–$BF go through `core_ld`/`core_st` in MODE_RAM. **One deviation from "fast path for $0000–$7FFF":
the page $7F00–$7FFF also takes the slow path.** With `(zp),y`, a pointer in $7Fxx plus Y can reach $8000–$80FE,
which would read flash on the fast path. Checking the effective address instead (pointer + Y) would add about 10
cycles to every access; treating one page as slow costs 41 cycles only on accesses there [Certain for the
correctness: T1 tests $7F80+$C0 = $8040 and $7FFF+1; the mutation without this rule fails]. $BFxx + Y crossing into
$C0xx is correct either way. High bytes $D0–$FF are on the "fast" side, so FETCH there reads I/O or the KERNAL as
in MODE_HOME; the workspace ends at $CFFF, and data under I/O or the KERNAL goes through IOFETCH/IOSTORE or
`core_ld`/`core_st`.

The slow helpers take their zero-page pointer as a self-modified operand (`core_ldop+1`, `core_stop+1`), written by
the macro. That keeps one routine for every pointer; the interrupt wrappers save and restore both operands, so
interrupt code may use FETCH/STORE too (the stress test does).

## Interrupts

Every IRQ and NMI ends up in the KERNAL's own entry points with MODE_HOME and bank 0 mapped, and goes back to the
interrupted memory configuration and bank. Nothing in the interrupt path uses a fixed temporary; it all lives on the
stack, so NMIs inside IRQs and interrupts inside the helpers are safe [Certain for what the stress test covers].

| Interrupted in | CPU takes its vector from | Path |
|---|---|---|
| MODE_HOME (flash code, any bank), or $36 | KERNAL ROM | IRQ: $FF48 → ($0314) = `core_irq`: save $01, `core_bank` and both helper operands; MODE_HOME, bank 0; JSR (`core_irqvec`); restore; `jmp $EA31`. NMI: $FE43 → ($0318) = `core_nmi`: same saves, fake RTI frame, `jmp (core_nmivec)` (default $FE47); the handler's RTI comes back to restore. |
| MODE_RAM / MODE_ALL (inside a helper) | RAM at $FFFA/$FFFE | `ram_irq`/`ram_nmi` at $FFxx: save A and $01, push a fake frame, MODE_RAM, jump to $DFxx, MODE_HOME, enter the KERNAL at $FF48/$FE43 as the CPU would. The KERNAL's RTI returns to $DFxx, which goes back through $FFxx to restore $01 and RTI. |

- Overhead per IRQ over the plain KERNAL path: about 97 cycles in MODE_HOME, about 70 more when it hits a helper
  window [Likely: counted from the code, not measured]. At 60 Hz that is about 0.6% of the CPU.
- NMI maps bank 0 before the KERNAL's NMI code runs, so RESTORE reaches the warm start ($A002) of bank 0
  whichever bank was mapped. BRK ($0316 → $FE66 → ($A002)) does not go through the core yet: every bank must
  then carry the same warm-start vector at $A002, or $0316 gets a core entry too (task 2.2).
- The KERNAL entry points used ($FF48, $FE43, $FE47, $EA31) are identical in the stock and JiffyDOS 6.01 KERNALs
  at their entries; $EA31 differs only in the tape-motor part (step 2.0) [Certain, byte comparison].
- Not supported, as on a stock C64 with the KERNAL's handler: interrupts while code runs with $01 = $30–$33
  (character ROM in, I/O out). Programs that copy the character ROM do that with SEI.
- The 6502 keeps the D flag on interrupt entry; the KERNAL does not clear it. Same as stock.

## Far calls

`+FAR target, bank` builds a 26-byte stub. The caller `jsr`s it; the stub pushes P, A, X, the old bank and a
return into the core, then the core switches $DE00 (shadow first, so an interrupt in between restores the right
bank), restores A, X and P and enters the target. The target's results come back the same way, and the old bank is
mapped again. Nested far calls work (T4: bank 0 → 1 → 0 → 1 → 0, all registers checked at each level).

204 cycles round trip is expensive, so hot code should not cross banks. A layout that keeps calls inside a bank
[Guessing, for 2.2/4.1]: the patched interpreter in ROMH of every bank (identical copies; flash is plentiful) and
TSB's code spread over the ROML halves, so TSB's 57 calls into BASIC never cross banks and only TSB-to-TSB calls
between ROML banks need stubs.

## What this means for the next tasks

- **Speed (D4, task 2.4):** every pointer access in the interpreter gets slower: a fast FETCH costs 3x a plain
  `lda (zp),y`, a fast STORE 5x a plain `sta`. How much that slows BASIC depends on how often the interpreter
  dereferences pointers compared with everything else. CHRGET is the hottest: it reads the program text through
  TXTPTR in zero page and must be rewritten around the same idea (task 2.2). Possible savings, if 2.4 needs them:
  a STORE variant without the flag save where the call site does not need flags (about 8 cycles less), and keeping
  hot data (variables, strings) below $8000 or in $C000–$CFFF. [Guessing] that the slowdown lands near the plan's
  18–25%; 2.4 measures it.
- **Task 2.2** (plain BASIC V2 from flash, 51,199 bytes free): CHRGET in RAM with the slow path, BRK/RESTORE vectors
  for every bank, the interpreter's pointer accesses through FETCH/STORE.
- **Task 2.3** (U2+ graphics): block fill/copy under I/O will need faster helpers than byte-wise IOSTORE (83 cycles a
  byte); a page-at-a-time routine in the $FF40 area is the obvious next step.
- **Task 2.5** (real hardware): the three memory modes, EasyFlash RAM visibility in 16K mode, and the RAM vectors
  are VICE results until then.
